# ขั้นตอนการแจ้งเหตุละเมิดข้อมูลส่วนบุคคล (มาตรา 37(4) — ภายใน 72 ชั่วโมง)
## ระบบยืนยันตัวตนผู้สมัครสมาชิกพรรคด้วย ThaID (KYC broker)

> **ร่าง v0.1 — ยังไม่มีผลบังคับใช้**
> ต้องให้เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) และที่ปรึกษากฎหมายของพรรคตรวจสอบและรับรอง
> ก่อนนำระบบขึ้นใช้จริง (`VERIFY_ENABLED=true`, `VERIFY_DRIVER=oidc`)
>
> ช่องที่เป็น `[...]` = ต้องเติมข้อมูลทางการของพรรค
> อ้างอิง: [`DPIA.md`](./DPIA.md) ข้อ 6 (มาตรการองค์กร) และตารางความเสี่ยง R1–R4, R9;
> ปิด checkbox ที่เกี่ยวข้องใน [`GO-LIVE.md`](./GO-LIVE.md) ข้อ 3

## 1. คำนิยาม — เหตุอะไรเข้าข่าย "เหตุละเมิดข้อมูลส่วนบุคคล" ในระบบนี้

เหตุการณ์ที่ทำให้ข้อมูลส่วนบุคคลถูกทำลาย สูญหาย เข้าถึง ใช้ เปลี่ยนแปลง หรือเปิดเผยโดยไม่ได้รับอนุญาต
หรือโดยไม่ชอบด้วยกฎหมาย — ตัวอย่างที่เข้าข่ายในระบบนี้โดยเฉพาะ (ดู `DPIA.md` ตารางความเสี่ยงข้อ 5):

- คีย์ลับ (`VERIFY_FIELD_KEY`, `VERIFY_S2S_SECRET`, `VERIFY_PID_PEPPER`) หลุดออกไปนอกระบบ
- มีการเข้าถึง `register_verification` หรือ `verify_prefill_cache` โดยไม่ได้รับอนุญาต
- กลไกยืนยันตัวตนระหว่างระบบ (S2S) ถูกข้ามหรือปลอมแปลงได้ — เช่น ช่องโหว่ประเภท
  IP allowlist ถูก bypass ผ่านการปลอม header (คลาสของช่องโหว่ที่เคยพบและแก้ไขแล้วในโค้ด
  `server/verify/s2s.ts` — ดูตัวอย่างคลาสความเสี่ยงนี้ประกอบ ไม่ใช่เหตุการณ์ที่เกิดขึ้นจริง)
- ข้อมูลตัวตน/token/claims จาก ThaID หลุดเข้า log โดยผิดนโยบาย (ห้าม log ตาม `DPIA.md` ข้อ 4)
- เซิร์ฟเวอร์ VPS ที่รันระบบถูกเจาะ (unauthorized access)
- พนักงาน/เจ้าหน้าที่เข้าถึงผล KYC เกินขอบเขตหน้าที่ (insider access)

## 2. ขั้นตอน 4 ระยะ

### ระยะที่ 1 — ตรวจพบ (T0)

ผู้ที่พบสัญญาณผิดปกติ (developer, ผู้ดูแลระบบ, เจ้าหน้าที่พรรค, หรือผู้ใช้แจ้งเข้ามา) **ต้องแจ้ง
DPO และผู้ดูแลระบบทันที** ผ่านช่องทาง: `[ระบุช่องทางฉุกเฉิน เช่น กลุ่มไลน์/เบอร์โทรที่ติดต่อได้ตลอด 24 ชม.]`

**บันทึกเวลาที่ตรวจพบ (T0) ทันที — นาฬิกา 72 ชั่วโมงตามมาตรา 37(4) เริ่มนับจากจุดนี้**
(นับจาก "ทราบเหตุ" ไม่ใช่จาก "เหตุเกิดขึ้นจริง" ซึ่งอาจเป็นคนละเวลากัน)

### ระยะที่ 2 — ควบคุมความเสียหาย (แนะนำให้เสร็จภายใน 4 ชั่วโมงจาก T0)

ผู้ดูแลระบบ:
- ตัดช่องทางที่เป็นต้นเหตุทันที (เช่น หมุน secrets ที่หลุด, ปิด `VERIFY_ENABLED` ชั่วคราว,
  บล็อก IP/credential ที่ผิดปกติ, revoke session ที่น่าสงสัย)
- **เก็บหลักฐานก่อนแก้ไขระบบ** (log, snapshot, ภาพหน้าจอ) เพื่อการสอบสวนภายหลัง — อย่าลบ log
  ที่อาจเป็นหลักฐาน แม้จะเป็น log ที่มีข้อมูลอ่อนไหวก็ควรเก็บแยกไว้ในที่ปลอดภัย ไม่ใช่ลบทิ้ง

DPO เริ่มประเมินขอบเขตเบื้องต้นคู่ขนาน:
- ข้อมูลประเภทใดหลุด/ถูกเข้าถึง (ดูตารางประเภทข้อมูลใน `DPIA.md` ข้อ 2.2)
- กระทบผู้สมัคร/สมาชิกกี่รายโดยประมาณ
- ความเสี่ยงต่อสิทธิเสรีภาพของเจ้าของข้อมูลอยู่ระดับใด (ใช้กรอบเดียวกับ `DPIA.md` ข้อ 5)

### ระยะที่ 3 — ประเมิน + แจ้ง สคส. (ต้องแจ้งภายใน 72 ชั่วโมงจาก T0 หากเข้าเกณฑ์)

1. DPO ร่วมกับที่ปรึกษากฎหมายประเมินว่าเข้าเกณฑ์ต้องแจ้งสำนักงานคณะกรรมการคุ้มครองข้อมูล
   ส่วนบุคคล (สคส.) ตามมาตรา 37(4) หรือไม่ — เกณฑ์คือมีความเสี่ยงที่จะมีผลกระทบต่อสิทธิ
   เสรีภาพของเจ้าของข้อมูล (ไม่ใช่ทุกเหตุการณ์ต้องแจ้ง แต่ทุกเหตุการณ์ต้อง **ประเมิน**)
2. หากเข้าเกณฑ์: แจ้ง สคส. **ภายใน 72 ชั่วโมงนับจาก T0** ผ่านช่องทาง
   `[ระบุช่องทางแจ้งเหตุของ สคส. ที่ใช้งานอยู่ ณ ขณะนั้น]` โดยเนื้อหาต้องครอบคลุม
   (ดูแบบร่างข้อ 4):
   - ลักษณะของเหตุละเมิด
   - ประเภทและจำนวนข้อมูล/เจ้าของข้อมูลที่ได้รับผลกระทบโดยประมาณ
   - ผลกระทบที่อาจเกิดขึ้น
   - มาตรการที่ดำเนินการไปแล้วและที่วางแผนจะทำ
   - ชื่อและช่องทางติดต่อ DPO
3. หากยังประเมินไม่แล้วเสร็จภายใน 72 ชั่วโมง — แจ้ง สคส. ด้วยข้อมูลเท่าที่มี พร้อมระบุว่า
   จะส่งข้อมูลเพิ่มเติมตามมาเมื่อการสอบสวนคืบหน้า (ไม่ต้องรอให้สอบสวนเสร็จสมบูรณ์ก่อนแจ้ง)
4. หากความเสี่ยงสูงต่อสิทธิเสรีภาพของเจ้าของข้อมูล (ม.37(4) วรรคสอง) — **ต้องแจ้งเจ้าของข้อมูล
   ที่ได้รับผลกระทบด้วย** พร้อมมาตรการเยียวยาและคำแนะนำ (เช่น ควรระวังการถูกแอบอ้าง)

### ระยะที่ 4 — แก้ไข + สรุปบทเรียน (หลัง 72 ชั่วโมง)

- แก้ไขสาเหตุที่แท้จริง (root cause) ให้ถาวร ไม่ใช่แค่ปิดช่องทางชั่วคราว
- เขียนรายงานสรุปเหตุการณ์ (post-mortem) ครอบคลุม: สาเหตุ, timeline, ผลกระทบจริง,
  การแก้ไขที่ทำ, มาตรการป้องกันไม่ให้เกิดซ้ำ
- ทบทวน `DPIA.md` ใหม่ (ข้อ 9 กำหนดว่า "เกิดเหตุละเมิด" เป็นเงื่อนไขต้อง trigger ทบทวน)
- เก็บรายงานทั้งหมด (รวมที่แจ้ง สคส.) ไว้เป็นหลักฐานตามระยะเวลาที่กฎหมายกำหนด

## 3. ตารางบทบาทและความรับผิดชอบ

| บทบาท | หน้าที่ในเหตุการณ์ |
|---|---|
| ผู้พบเหตุ (คนใดก็ได้) | แจ้ง DPO + ผู้ดูแลระบบทันที บันทึกเวลาที่พบ |
| ผู้ดูแลระบบ (engineer) | ควบคุมความเสียหาย, เก็บหลักฐาน, แก้ไขทางเทคนิค |
| DPO | ประเมินขอบเขต, ตัดสินใจ/ประสานแจ้ง สคส., แจ้งเจ้าของข้อมูลถ้าจำเป็น, เก็บบันทึกเหตุการณ์ |
| ที่ปรึกษากฎหมาย | ร่วมประเมินเกณฑ์การแจ้ง สคส., ตรวจสอบข้อความที่จะแจ้ง |
| ผู้บริหารพรรค | รับทราบ, อนุมัติมาตรการที่มีผลกระทบสูง (เช่น ปิดระบบชั่วคราว, แจ้งสมาชิกจำนวนมาก) |

1. วันเวลาที่ทราบเหตุ (T0): [...]

- เอกสารนี้ปิด checkbox `ขั้นตอนแจ้งเหตุละเมิด 72 ชม. (ม.37)` ใน [`GO-LIVE.md`](./GO-LIVE.md) ข้อ 3
  เมื่อ DPO + ที่ปรึกษากฎหมายรับรองแล้ว
- ช่องทางแจ้งเหตุฉุกเฉินในข้อ 2 (ระยะที่ 1) ควรทดสอบว่าใช้งานได้จริงก่อน go-live ไม่ใช่ตั้งไว้เฉย ๆ
- แนะนำผูกเรื่องนี้เข้ากับ R9 ใน `DPIA.md` (ย้าย secret ไป Vault — โค้ดพร้อมแล้ว รอ deploy จริง
  ดู `integration/vault/`) — คีย์ที่ยังอยู่ใน `.env`
  ธรรมดาเพิ่มโอกาสเกิดเหตุประเภท "คีย์ลับหลุด" ตามข้อ 1
- เมื่อเปิด access log ตาม R5 ใน `DPIA.md` แล้ว จะช่วยให้ระยะที่ 2 (ควบคุมความเสียหาย) ประเมิน
  ขอบเขตได้เร็วขึ้นมาก — ควรทำคู่กันกับเอกสารนี้
