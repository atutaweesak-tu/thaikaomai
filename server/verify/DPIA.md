# DPIA — การประเมินผลกระทบด้านการคุ้มครองข้อมูลส่วนบุคคล
## ระบบยืนยันตัวตนผู้สมัครสมาชิกพรรคด้วย ThaID (KYC broker)

> **ร่าง v0.1 — ยังไม่มีผลบังคับใช้**
> ต้องให้เจ้าหน้าที่คุ้มครองข้อมูลส่วนบุคคล (DPO) และที่ปรึกษากฎหมายของพรรคตรวจสอบและรับรอง
> ก่อนนำระบบขึ้นใช้จริง (`VERIFY_ENABLED=true`, `VERIFY_DRIVER=oidc`)
>
> ช่องที่เป็น `[...]` = ต้องเติมข้อมูลทางการของพรรค
> อ้างอิงระบบ: `server/verify/` (broker) + `server/verify/integration/` (api/SPA) — commit `f7a3e33` (2026-09-02)

## 2. คำอธิบายการประมวลผล

### 2.1 วัตถุประสงค์

1. ยืนยันว่าผู้สมัครสมาชิกเป็นบุคคลจริง มีสัญชาติไทย และมีตัวตนตามทะเบียนราษฎร
2. ยืนยันว่าชื่อ–สกุล เลขประจำตัวประชาชน 13 หลัก วันเดือนปีเกิด และที่อยู่ตามทะเบียนบ้าน
   ที่ผู้สมัครแจ้ง ตรงกับฐานกรมการปกครอง
3. ลดข้อผิดพลาดของบัญชีสมาชิกพรรค ซึ่งมีผลตามกฎหมายพรรคการเมือง/การเลือกตั้ง และลดภาระ
   การตรวจเอกสารด้วยมือของเจ้าหน้าที่

การยืนยันตัวตนนี้เป็น **ทางเลือกเสริม** — ผู้สมัครที่ไม่ใช้ ThaID ยังสมัครได้ตามปกติ
และเจ้าหน้าที่ตรวจเอกสารด้วยวิธีเดิม

### 2.2 ประเภทข้อมูลส่วนบุคคล

| ข้อมูล | ประเภท | เก็บถาวรหรือไม่ |
|---|---|---|
| การสมัคร/เป็นสมาชิกพรรคการเมือง | **อ่อนไหว** (ม.26 — ความเห็นทางการเมือง) | เก็บ (ในระบบสมัครเดิม — นอกขอบเขต DPIA นี้ ระบบ KYC เพียงผูก flag) |
| เลขประจำตัวประชาชน 13 หลัก | ข้อมูลที่ต้องระวังเป็นพิเศษ (ตามแนวปฏิบัติ สคส.) | **ไม่เก็บค่าจริง** — เก็บเฉพาะ `id_card_hash` = HMAC-SHA256(เลขบัตร, pepper) |
| ชื่อ–สกุล (ภาษาไทย) | ทั่วไป | ไม่เก็บในระบบ KYC (ไปอยู่ในใบสมัครปกติ) |
| วันเดือนปีเกิด | ทั่วไป | ไม่เก็บในระบบ KYC |
| ที่อยู่ตามทะเบียนบ้าน | ทั่วไป | ไม่เก็บในระบบ KYC |
| ผลการยืนยัน: is_thai_national / name_match / birthdate_match / address_match / overall_pass | ทั่วไป (อนุมาน) | **เก็บ** (flag ล้วน ในตาราง `register_verification`) |
| ระดับความเชื่อมั่นตัวตน (IAL), รหัสธุรกรรม NDID (`ndid_request_id`), ผู้ให้บริการ | ทั่วไป | เก็บ (audit) |
| บันทึกความยินยอม: `consent_version`, `consent_at` | ทั่วไป | เก็บ |
| IP ผู้ร้องขอ (`requester_ip`), เวลายืนยัน (`verified_at`) | ทั่วไป | เก็บ (audit) |

### 2.3 เจ้าของข้อมูล

ประชาชนสัญชาติไทยที่สมัครเป็นสมาชิกพรรค และเลือกใช้ ThaID ยืนยันตัวตน

### 2.4 ผู้รับข้อมูล / การเปิดเผย

- **ภายในพรรคเท่านั้น** — ผลการยืนยันแสดงเป็น badge (✅ ยืนยันแล้ว / ⏳ รอ / ❌ ไม่ผ่าน / — ไม่ได้ทำ)
  ให้เจ้าหน้าที่ตรวจใบสมัครเห็น จำกัดสิทธิ์ตามบทบาท
- **ไม่มี** การเปิดเผยต่อบุคคลภายนอก ไม่มีการส่งให้ผู้ให้บริการวิเคราะห์/โฆษณา ไม่มีการขาย
- **ไม่มีการส่งข้อมูลออกนอกราชอาณาจักร** — ระบบทั้งหมดทำงานบนเซิร์ฟเวอร์ของพรรค `[ยืนยันที่ตั้ง data center ในไทย]`

### 2.5 ระยะเวลาเก็บรักษา (Retention)

| ที่เก็บ | เนื้อหา | ระยะเวลา |
|---|---|---|
| `verify_sessions` (broker, SQLite) | match fields เข้ารหัส AES-256-GCM | อายุสั้น (ค่าเริ่มต้น ≤ 30 นาที); `match_fields_enc` ถูกล้างเป็น NULL ทันทีที่ handoff เสร็จ; sweep ทุก 5 นาที |
| `verify_prefill_cache` (api) | VerifiedProfile เข้ารหัส (เฉพาะโหมด prefill) | ~10 นาที, ใช้ได้ครั้งเดียว (`consumed_at`), sweep ทิ้ง |
| `register_verification` (api) | ผล KYC (flag ล้วน) + `id_card_hash` + บันทึกความยินยอม + audit | **`[ต้องกำหนดเป็นทางการ]`** — ข้อเสนอ: ตราบที่ยังเป็นสมาชิก + `[X]` ปีหลังพ้นสภาพสมาชิก เพื่อการตรวจสอบ/ระงับข้อพิพาท/หน้าที่ตามกฎหมายเลือกตั้ง จากนั้นลบหรือทำให้ไม่สามารถระบุตัวบุคคลได้ |

`id_card_hash` (ไม่ใช่เลขบัตรจริง) ใช้ตรวจการสมัครซ้ำ/ค้นหาบันทึกได้โดยไม่ต้องเก็บเลข 13 หลัก

## 3. ความจำเป็นและได้สัดส่วน

### 3.1 ฐานการประมวลผล

| การประมวลผล | ฐานที่ใช้ | หมายเหตุ (ให้ DPO ยืนยัน) |
|---|---|---|
| ประมวลผลข้อมูลเพื่อยืนยันตัวตนกับ DOPA (รวมเลขบัตร) | **ความยินยอมโดยชัดแจ้ง** (ม.26 ประกอบ ม.19) เก็บ version + เวลา | ThaID กำหนดให้ต้องมีความยินยอมของผู้ใช้ต่อธุรกรรมอยู่แล้ว พรรคขอความยินยอมของตนเองเพิ่มเพื่อความชัดเจน |
| เก็บบันทึกผลยืนยัน/การเป็นสมาชิกไว้ภายในพรรค | ม.26(3) — กิจกรรมโดยชอบด้วยกฎหมายขององค์กรที่มีวัตถุประสงค์ทางการเมือง กระทำต่อสมาชิก และ **ไม่เปิดเผยออกภายนอก** | สอดคล้องเงื่อนไข: กระทำต่อสมาชิก + ไม่เปิดเผยออกนอกพรรค |
| ประมวลผลข้อมูลทั่วไป (ชื่อ/วันเกิด/ที่อยู่) ในใบสมัคร | ม.24 — ความยินยอม / จำเป็นเพื่อประโยชน์โดยชอบด้วยกฎหมาย | เป็นการประมวลผลเดิมของระบบสมัคร ไม่เปลี่ยนแปลง |

### 3.2 การลดข้อมูลให้เหลือเท่าที่จำเป็น (Data Minimization)

- **โหมด match (verify-after):** ส่งเฉพาะ field ที่ต้องเทียบให้ broker → เทียบแล้ว **คืนเป็น flag เท่านั้น** →
  broker ทิ้งข้อมูลดิบ ไม่มีสำเนา claims จาก DOPA ค้างที่ฝั่ง broker
- **โหมด prefill (verify-first):** ส่ง seed แค่เลขบัตร → DOPA คืนโปรไฟล์ที่ยืนยันแล้ว → **เข้ารหัส เก็บชั่วคราว
  ใช้ครั้งเดียว** ให้ SPA เติมฟอร์ม → ลบ; ข้อมูลที่ผู้ใช้ยืนยันจะไปอยู่ในใบสมัครปกติ (การประมวลผลเดิม)
- **ไม่เก็บ:** เลขบัตร 13 หลัก plaintext, สำเนาบัตรประชาชน, ภาพถ่าย, ข้อมูลชีวมิติ, token/claims ดิบจาก IdP
- เก็บ `id_card_hash` (HMAC + pepper แยก key) แทนเลขบัตร เพื่อกันสมัครซ้ำ/ค้นหา โดยไม่ต้องถือ PID

### 3.3 ทางเลือกที่พิจารณาแล้ว

| ทางเลือก | เหตุผลที่ไม่เลือก / ที่เลือก |
|---|---|
| อัปโหลดสำเนาบัตร + ตรวจด้วยคน | เก็บสำเนาบัตร = ความเสี่ยงสูงกว่ามาก, ตรวจด้วยตาไม่แม่น → **คงไว้เป็น fallback** ไม่ใช่หลัก |
| เก็บเลขบัตร 13 หลัก plaintext เพื่อ dedupe | ไม่จำเป็น — `id_card_hash` ทำหน้าที่นี้ได้ → **ไม่เก็บ** |
| ให้ broker เก็บผล KYC ถาวร | ไม่จำเป็น — ฝั่ง api (ระบบสมัคร) เก็บพอ → broker **เก็บแค่ session ชั่วคราว** |
| ใช้ ThaID (OIDC + PKCE, IAL ≥ 2.3) | มาตรฐานรัฐ, ผู้ใช้ควบคุมการเปิดเผยผ่านแอปตนเอง → **เลือกใช้** |

## 4. การไหลของข้อมูล

ดูแผนภาพเต็มใน [`README.md`](./README.md) หัวข้อ "Flow" — สรุป:

```
ผู้สมัคร (SPA)  ──(1) POST /api/verify/start {เลขบัตร, consent.version}──►  api พรรค
api  ──(2) S2S เปิด session (+consent.acceptedAt = เวลา server)──►  broker พรรค
ผู้สมัคร  ──(3) redirect ไป /verify?sid=… (ไม่มี PII ใน URL)──►  broker  ──►  ThaID/DOPA
ThaID  ──(4) callback + id_token/claims──►  broker  ── ตรวจลายเซ็น/IAL/nonce, map → VerifiedProfile
broker  ──(5) S2S push ผล {flags, id_card_hash, consent, [profile ถ้า prefill]}──►  api พรรค
api  ── บันทึก register_verification (flag ล้วน) [+ cache profile เข้ารหัส ถ้า prefill]
ผู้สมัคร  ──(6) redirect กลับ /register?vs=<sid>&kyc=verified──►  SPA
SPA  ──(7) GET /api/verify/prefill?vs=<sid> (ครั้งเดียว)──►  api  ── ถอดรหัส คืน profile → เติมฟอร์ม+ล็อก → cache ลบ
```

**จุดที่ข้อมูลอ่อนไหวปรากฏและถูกป้องกัน:**

| จุด | ข้อมูล | การป้องกัน |
|---|---|---|
| URL redirect | เฉพาะ `sid` (สุ่ม 24 ไบต์) | ไม่มี PII ใน query string |
| broker ↔ api (S2S) | payload มี flag + hash (+ profile ถ้า prefill) | TLS + HMAC-SHA256(timestamp.nonce.body) + กัน replay 5 นาที + IP allowlist |
| ที่พักใน broker (`verify_sessions`) | match fields | AES-256-GCM, ล้างทันทีหลัง handoff, sweep 5 นาที |
| ที่พักใน api (`verify_prefill_cache`) | VerifiedProfile | AES-256-GCM, TTL ~10 นาที, single-use |
| id_token / access_token / claims จาก IdP | เลขบัตร, ชื่อ, ที่อยู่ | **ห้าม log** (กำหนดไว้ในโค้ด `oidc.ts` / `identityVerifier.ts`); ใช้แล้วทิ้งใน memory |
| ที่เก็บถาวร (`register_verification`) | flag + `id_card_hash` + consent + audit | ไม่มี PID/ชื่อ/ที่อยู่; hash ใช้ pepper แยก key |

## 5. การประเมินความเสี่ยงต่อสิทธิและเสรีภาพของเจ้าของข้อมูล

ระดับ: L = ต่ำ, M = ปานกลาง, H = สูง (โอกาสเกิด × ความรุนแรง)

| # | ความเสี่ยง | ก่อนมาตรการ | มาตรการ | หลังมาตรการ |
|---|---|:---:|---|:---:|
| R1 | เลขบัตร 13 หลักรั่วไหลจากที่เก็บถาวร | H | ไม่เก็บ plaintext; เก็บ HMAC+pepper, pepper แยกจาก DB | L |
| R2 | โปรไฟล์ที่ยืนยันแล้วถูกดักระหว่าง prefill | M | เข้ารหัส AES-GCM, single-use, TTL 10 นาที, `sid` สุ่ม, TLS | L |
| R3 | S2S ถูกปลอม/เล่นซ้ำ → ยัดผลปลอม/ดึงสถานะ | M | HMAC ต่อ request + timestamp skew 5 นาที + nonce + IP allowlist | L |
| R4 | ThaID token/claims หลุดผ่าน log | M | นโยบายห้าม log PID/token/claims (บังคับในรีวิวโค้ด); ใช้แล้วทิ้ง | L |
| R5 | เจ้าหน้าที่พรรคเข้าถึงผล KYC เกินความจำเป็น | M | สิทธิ์ตามบทบาท, แสดงแค่ badge ✅/❌, บันทึก log การเข้าถึง `[ต้องเปิดใช้]` | L–M |
| R6 | เก็บข้อมูลนานเกินจำเป็น | M | Retention policy + งานลบ/ทำ anonymize อัตโนมัติ `[ต้องกำหนด+ทำ]` | L |
| R7 | เจ้าของข้อมูลใช้สิทธิ (เข้าถึง/แก้ไข/ลบ/คัดค้าน/ถอนยินยอม) ได้ยาก | M | ขั้นตอนรองรับผ่าน DPO; ค้นบันทึกด้วย `id_card_hash` โดยไม่ต้องขอ PID เต็ม `[ต้องจัดทำขั้นตอน]` | L |
| R8 | การเชื่อมโยง/ทำโปรไฟล์ข้ามระบบ | L | broker ไม่เก็บถาวร, ไม่มี analytics/third-party, ข้อมูลอยู่ในพรรคเท่านั้น | L |
| R9 | `VERIFY_FIELD_KEY` อยู่ในไฟล์ `.env` (ไม่ใช่ KMS) | M | ควรย้ายไป KMS/secret manager ก่อน go-live (ระบุใน `GO-LIVE.md` ข้อ 2) | M → L เมื่อทำ |
| R10 | ผู้สมัครเข้าใจผิดว่า "ต้อง" ใช้ ThaID | L | ข้อความชัดว่าเป็นทางเลือก; fallback ตรวจเอกสารเดิมทำงานเสมอ | L |
| R11 | ThaID/DOPA ล่ม หรือเปลี่ยนสเปก claim | L | KYC ไม่ block การสมัคร; ปิด `VERIFY_DRIVER` กลับ `stub` ได้ทันที | L |

**ความเสี่ยงคงเหลือ (residual):** R5, R9 อยู่ระดับ M จนกว่าจะเปิด access log และย้าย key ไป KMS
เมื่อดำเนินการครบ ความเสี่ยงทั้งหมดอยู่ระดับ **ยอมรับได้** — ประเมินว่า **ไม่เข้าเงื่อนไขต้องปรึกษา สคส.
ล่วงหน้าตาม ม.36** แต่ต้องจัดเก็บ DPIA ฉบับนี้ไว้และทบทวนตามรอบ *(ให้ DPO ยืนยันคำวินิจฉัยนี้)*

## 6. มาตรการทางเทคนิคและองค์กร

### เทคนิค
- OIDC Authorization Code + PKCE (S256); ตรวจ `state` (constant-time), `nonce`, ลายเซ็น id_token กับ JWKS,
  `iss`/`aud`/`azp`/`exp`/`iat`/`nbf`, และ IAL ≥ `THAID_REQUIRED_IAL`
- เข้ารหัสข้อมูลระหว่างพัก: AES-256-GCM (`VERIFY_FIELD_KEY`)
- แฮชเลขบัตร: HMAC-SHA256 + pepper (`VERIFY_PID_PEPPER`) เก็บแยก
- S2S: HMAC ต่อ request + กัน replay + IP allowlist
- TLS ทุกช่องทาง (reverse proxy)
- อายุสั้น + ใช้ครั้งเดียว + sweep อัตโนมัติ สำหรับข้อมูลพัก
- ห้าม log ข้อมูลตัวตน/โทเคน
- แยก key management ไป KMS `[ก่อน go-live]`

### องค์กร
- แต่งตั้ง DPO และประกาศช่องทางติดต่อ `[ทำ]`
- Privacy notice เฉพาะเรื่อง KYC + ข้อความขอความยินยอม (ดู [`CONSENT.md`](./CONSENT.md))
- จำกัดสิทธิ์เข้าถึงผล KYC ตามบทบาท + เปิด access log `[ทำ]`
- กำหนด Retention policy เป็นลายลักษณ์อักษร + งานลบอัตโนมัติ `[ทำ]`
- ขั้นตอนรองรับการใช้สิทธิของเจ้าของข้อมูล + ขั้นตอนแจ้งเหตุละเมิด (72 ชม. ตาม ม.37) `[ทำ]`
- Data Processing Agreement กับผู้ให้บริการโครงสร้างพื้นฐาน `[ทบทวน]`
- Security assessment / penetration test ก่อนเปิดใช้ `[ทำ]`
- อบรมเจ้าหน้าที่ที่เกี่ยวข้อง `[ทำ]`

## 7. สิทธิของเจ้าของข้อมูล (ม.30–34)

| สิทธิ | รองรับอย่างไร |
|---|---|
| เข้าถึง/ขอสำเนา | ผ่าน DPO — ระบุเฉพาะ flag ผลยืนยัน + เวลา + เวอร์ชัน consent (ไม่มี PID ในระบบให้คืน) |
| แก้ไขให้ถูกต้อง | ผลไม่ตรง → ยืนยันใหม่ หรือให้เจ้าหน้าที่ตรวจเอกสารแทน |
| ลบ/ทำลาย | ลบ `register_verification` ของบุคคลนั้น (ค้นด้วย `id_card_hash` หรือ `register_log_id`) เว้นแต่มีหน้าที่ตามกฎหมายให้เก็บ |
| คัดค้าน/ระงับ | หยุดใช้ผล KYC กับใบสมัครนั้น กลับไปตรวจด้วยมือ |
| ถอนความยินยอม | ทำได้ทุกเมื่อ ไม่กระทบการประมวลผลก่อนถอน; ผลต่อสมาชิกภาพ ดู [`CONSENT.md`](./CONSENT.md) หมวด C |
| โอนย้ายข้อมูล | ไม่เกี่ยวข้องในทางปฏิบัติ (ระบบเก็บเพียง flag/hash) |

## 8. ความเห็นสรุป

- การประมวลผลมี **ความจำเป็นและได้สัดส่วน** กับวัตถุประสงค์ (ความถูกต้องของบัญชีสมาชิกซึ่งมีผลตามกฎหมาย)
- ออกแบบตามหลัก **data minimization / privacy by design** — ไม่เก็บเลขบัตร ไม่เก็บสำเนาบัตร
  broker ไม่เก็บถาวร ข้อมูลพักมีอายุสั้นและเข้ารหัส
- ความเสี่ยงหลักถูกลดจนอยู่ในระดับยอมรับได้ เมื่อดำเนินการตามข้อ 6 ครบ
- **เงื่อนไขก่อนเปิดใช้จริง** (ดู `GO-LIVE.md`): (1) DPO + ที่ปรึกษากฎหมายรับรอง DPIA + ข้อความ consent,
  (2) กำหนด Retention policy + งานลบอัตโนมัติ, (3) ย้าย `VERIFY_FIELD_KEY` ไป KMS,
  (4) เปิด access log, (5) จัดทำขั้นตอนใช้สิทธิ + แจ้งเหตุละเมิด, (6) pen-test,
  (7) ทดสอบ `driver=oidc` กับ ThaID sandbox
